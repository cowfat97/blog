    输出格式控制（Agent 场景）

    Agent 开发中经常需要模型输出结构化内容（JSON / 工具调用指令），四种做法从简到严：

    1. 提示词约束（最简单）：system 里写「只输出 JSON，字段为 xxx，不要多余解释」。缺点：小模型可能不听话
    2. 结构化输出 / 约束解码（可靠）：不是「劝」是「锁」——outlines / xgrammar 把 JSON 规则转成状态机，模型每生成一个 token 都只能选语法合法的那个，结果保证是合法 JSON；vLLM 的 response_format: {"type": "json_object"} 同理
    3. 工具调用（Agent 主流）：模板里声明「我有哪些工具：查天气(城市)、算数(表达式)」，模型输出 {"name": "get_weather", "arguments": {...}} 调用指令，代码解析执行后把结果喂回模型，模型出最终回答。这是 Agent 的标准循环，Qwen3 训练过这个格式，输出天然规整
    4. 解析兜底：正则抠 JSON → pydantic 校验 → 不合格重试

    第 5 种手段是微调，但和前 4 种不是一类：前 4 种都是推理期技巧（不改模型，生成时生效），微调是训练期手段——让模型格式遵从能力本身变强（指令微调、function calling 数据微调）。前 4 种用尽还不满意（小模型格式遵从太差）才走这条路，成本最高（数据 + 算力）、收益根本性。

    类比：2 是导轨，3 是约定格式，4 是质检员。

    1 解析兜底完整实现

    四步：抠 → 解析 → 校验 → 重试。补上 model_generate 就能跑（模型加载同 01_quick_start.py）：

    import json
import re
from pydantic import BaseModel

class Person(BaseModel):      # 期望的字段结构
    name: str
    age: int

def model_generate(messages, max_new_tokens=256):
    """消息列表 → 模型输出文本"""
    text = tokenizer.apply_chat_template(
        messages, tokenize=False,
        add_generation_prompt=True, enable_thinking=False)
    inputs = tokenizer([text], return_tensors="pt").to(model.device)
    out = model.generate(**inputs, max_new_tokens=max_new_tokens,
                         do_sample=True, temperature=0.6, top_p=0.8, top_k=20)
    new_ids = out[0][len(inputs.input_ids[0]):]        # 截掉输入只留新生成的
    return tokenizer.decode(new_ids, skip_special_tokens=True)

def extract_json(text):
    m = re.search(r'\{.*\}', text, re.S)
    if not m:
        raise ValueError("没找到 JSON")
    raw = m.group(0)
    try:
        return json.loads(raw)
    except json.JSONDecodeError:
        return json.loads(re.sub(r',\s*([}\]])', r'\1', raw))  # 修尾逗号

def generate_and_parse(messages, max_retries=2):
    for _ in range(max_retries + 1):
        text = model_generate(messages)
        try:
            return Person(**extract_json(text))
        except Exception:
            # 把错误输出塞回对话，让模型看着自己错在哪重写
            messages.append({"role": "assistant", "content": text})
            messages.append({"role": "user",
                "content": f"你上次输出不是合法 JSON：{text[:200]}\n重新输出，只要 JSON。"})
    return text   # 降级：重试耗尽，返回原始文本，不让程序崩

# 调用
result = generate_and_parse(
    [{"role": "user", "content": "输出一个 JSON：姓名张三，年龄 30"}])
print(result.name, result.age)

    核心三点：messages 就是对话历史（重试 = 把错误答案和纠错要求追加进去再跑一轮）；extract_json 做抠 + 修 + 解析；重试耗尽 return text 是优雅降级。关键在带错误重试——把错误片段拼回 prompt 让模型看着自己的错重写，比无脑重试命中率高得多。

    2 重试仍失败：逐级降级

    按成本从低到高：

    1. 强化 prompt + few-shot：重试时把错误输出拼回 prompt，再给 1-2 个正确示例，小模型照葫芦画瓢成功率大增
    2. 约束解码（治本）：outlines / xgrammar 把 JSON 规则转成状态机，物理上保证合法 JSON
    3. 换更大模型：1.7B 格式遵从差，8B / API 大模型基本稳定
    4. 优雅降级：返回原始文本给上层，不让程序崩溃
    5. 长期：攒失败样本当微调数据

    3 约束解码原理

    3.1 生成一个 token 分两个环节

    「模型封装好了怎么还能控制输出」是常见误解。生成每个 token 其实是两步：

    1. 算分：模型吃进上文，吐出每个候选词的分数（logits）——这是模型干的，封装死的，谁也没动它
    2. 挑词：代码从这些分数里挑一个作为输出——这是调用方代码干的（transformers 的 generate 循环），模型不参与

    约束解码介入的是第 2 个环节——「挑」之前把非法选项划掉，模型算分的过程完全没变。模型只负责「算分」，代码负责「挑词」。

    类比：模型 = 给所有选项打分的机器；挑选项 = 读卡程序；约束解码 = 读卡前把非法选项涂黑。机器没改，是「看分挑词」这步加了过滤。temperature / top_k / top_p 也是同一层的操作——乘个系数、圈个池子，全是在 logits（一个 15 万的数字向量）上做数学操作。模型内部是黑盒，但它的接口（logits）是全透明的。

    3.2 状态机

    状态机（有限自动机）= 一个「当前状态 + 转移规则」的系统——知道自己在哪、下一步能去哪。生活例子：红绿灯——绿 → 黄 → 红 → 绿，当前是绿就只能变黄，不能直接跳红。正则表达式、电梯、自动售货机都是状态机。

    约束解码就是把「合法 JSON」的语法编译成状态机：

    • 状态 = 当前写到哪了：开始 → 刚写 { → 在写 key → 写完冒号 → 在写 value → 写完逗号 → ……
    • 每个状态只允许一部分 token：刚写完 { 只允许 " 或 }；写完冒号只允许值（字符串 / 数字 / { / [）；字符串中间不允许 " 提前出现

    3.3 从 Pydantic 到状态机：四步链路

    第 1 步：Pydantic → JSON Schema。Person 类自动导出结构描述：

    Person.model_json_schema()
# → {"type": "object", "properties": {"name": {"type": "string"}, "age": {"type": "integer"}}, ...}

    第 2 步：JSON Schema → 语法规则。outlines 把 Schema 展开成「合法输出长什么样」的规则，内部翻译成正则模式——{"name": "任意字符串", "age": 整数} 就是一个模式模板。

    第 3 步：规则 → 状态机。编译原理标准流程——正则 → 有限自动机（NFA → DFA → 最小化）。每个状态 = JSON 写到哪个位置，每条边 = 一个合法字符。这就是 generate.json(model_o, Person) 背后干的事。

    第 4 步：生成时掩码（约束生效的地方）。模型每生成一个 token：

    • 算 logits → 得到全部候选 token 的分数
    • 查状态机当前状态 → 只保留能合法接上的候选，其余 logits 设为 -∞（softmax 后概率 = 0）
    • 在合法候选中正常采样 → 状态机跟着走到新状态
    • 循环，直到写完 JSON

    屏蔽只是「划掉选项」，之后的挑选和正常生成完全一样——贪心取合法候选里分数最高的，采样在合法候选里按概率抽（概率重新归一化）。数字走一遍（刚写完 { 的状态）：

    • 模型打分（logits）：" 1.8、} 0.5、我 3.2（「我」分最高，但非法）
    • 状态机只允许 " 和 } → 我 的分数设为 -∞
    • softmax 后：" ≈ 0.79、} ≈ 0.21、我 = 0
    • 贪心 → 挑 "；采样 → 79% 挑 "、21% 挑 }

    约束解码不改变「怎么挑」，只改变「能在什么范围里挑」。代价是推理稍慢一点（每个 token 多一步掩码），换来零重试。

    3.4 实现

    from outlines import models, generate
model_o = models.Transformers(model, tokenizer)
generator = generate.json(model_o, Person)   # 输出物理上保证是合法 JSON

    Pydantic 只负责「描述结构」，outlines 负责「编译成状态机」，生成循环里「用状态机屏蔽非法 token」才是约束生效的点。每一步都是自动的，generate.json() 内部全包了。
