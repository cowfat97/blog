    Agent 统一工具输出与上下文预算实验

    实验背景

    长链路任务中，工具会产生文本、数字、对象、数组、表格、日志、图片和文件等不同类型的结果。如果把所有结果直接转成文本并截取开头，虽然能避免上下文溢出，但存在以下问题：

    • 大型 JSON 可能被截断成非法结构。
    • 关键状态、错误、统计值可能位于结果尾部。
    • 模型可能把局部样本误认为完整结果。
    • 不同工具的恢复方式不统一。
    • 工具结果不断累积，最终仍会占满上下文。

    本实验不依赖模型猜测哪些字段重要，而是要求工具或适配器输出统一的 ToolResult JSON 协议。上下文构建器固定保留控制字段，只对业务数据 data 执行分级缩减。

    实验目标

    验证以下方案能否在限制工具结果 Token 的同时，保证状态、错误、关键事实和完整结果恢复入口不丢失：

    原始工具结果
→ 标准 ToolResult Adapter
→ 完整结果持久化
→ 固定字段提取
→ data 分级缩减
→ 最终 Token 计数
→ 注入模型上下文

    重点回答：

    1. 不同类型工具能否使用统一的外层协议？
    2. 固定字段是否能避免关键状态被裁掉？
    3. data 超出预算时如何稳定降级？
    4. 完整结果能否通过 artifact_id、分页或 JSONPath 恢复？
    5. 相比文本前缀截断，结构化方案是否提高任务正确率？

    核心假设

    统一的是工具结果的控制协议，不是所有工具的业务字段。

    固定外层字段：

    {
  "ok": true,
  "tool": "tool_name",
  "result_type": "object",
  "summary": {},
  "data": {},
  "artifact": null,
  "pagination": null,
  "error": null,
  "meta": {}
}

    其中：

    字段 作用 上下文策略
    ok 工具是否成功 必须完整保留
    tool 工具名称 必须完整保留
    result_type 结果类型 必须完整保留
    summary 有限摘要与关键事实 必须保留并限制大小
    data 业务结果或有限样本 根据剩余预算缩减
    artifact 完整结果引用 必须完整保留
    pagination 后续读取位置 必须完整保留
    error 标准错误信息 失败时必须完整保留核心字段
    meta 大小、耗时等信息 仅保留白名单字段

    标准字段约束

    summary

    summary 不允许成为另一个无限文本字段，使用固定结构：

    {
  "status": "success",
  "message": "查询完成",
  "facts": [
    {
      "name": "row_count",
      "value": 100000,
      "unit": "rows"
    }
  ]
}

    约束：

    • status 使用固定枚举。
    • message 最多 500 个字符。
    • facts 最多 20 项。
    • fact.value 只允许标量或短字符串。
    • 关键业务事实由工具明确写入 facts，不由模型从大型 JSON 中猜测。

    error

    {
  "code": "DATABASE_TIMEOUT",
  "message": "数据库查询超时",
  "retryable": true,
  "details": {}
}

    固定保留 code、message、retryable，details 根据预算缩减。

    artifact

    {
  "id": "artifact_123",
  "format": "jsonl",
  "size_bytes": 19283102,
  "path": "tool_results/artifact_123.jsonl"
}

    只有完整结果持久化成功后，才允许缩减 data。保存失败时不得静默丢弃原始结果。

    result_type

    第一阶段支持以下类型：

    scalar
object
list
table
text
log
file
image
binary
error

    无法识别的第三方结果由 FallbackAdapter 转换为 text，完整内容落盘后提供有限预览。

    上下文预算规则

    假设单次工具结果预算为 2,000 Token：

    内容 预算示例
    外层控制字段 100 Token
    summary 400 Token
    error 300 Token
    artifact 100 Token
    pagination 100 Token
    data 最多 1,000 Token

    实际执行时不只依赖静态分配，还要对最终序列化结果进行模型 Tokenizer 计数。

    固定保留顺序：

    ok / tool / result_type
→ error
→ summary
→ artifact
→ pagination
→ meta 白名单
→ data

    当固定字段本身超过预算时：

    1. 缩短 summary.message。
    2. 减少普通 facts，但保留工具声明的必需事实。
    3. 移除 error.details，保留错误核心字段。
    4. 最低限度保留状态、错误和 artifact 指针。
    5. 如果最低限度仍无法装入，明确返回 context_unfit，禁止静默截断。

    data 分级缩减

    scalar

    数字、布尔值和空值完整保留：

    {
  "value": 18329,
  "unit": "users"
}

    object

    依次执行：

    1. 完整保留小对象。
    2. 保留工具声明的 important_paths。
    3. 保留根层短标量。
    4. 长字符串替换为长度、短预览和 artifact 路径。
    5. 深层对象替换为路径指针。

    list

    依次降级：

    全部元素
→ 头 10 项 + 尾 5 项
→ 头 3 项 + 尾 2 项
→ 仅元素 Schema、总数和 artifact

    必须同时返回：

    {
  "total_items": 100000,
  "returned_items": 5,
  "omitted_items": 99995
}

    table

    优先保留：

    • 总行数与总列数。
    • 列名和数据类型。
    • 工具预先计算的统计值。
    • 少量头尾样本。
    • 完整表格 artifact。

    log

    优先保留：

    • 退出码。
    • ERROR、FATAL、异常堆栈。
    • 开头少量启动信息。
    • 末尾最近状态。
    • 完整日志 artifact。

    image、file、binary

    二进制内容不序列化进 JSON 文本，只保留：

    • artifact ID 和路径。
    • MIME 类型、大小、尺寸或哈希。
    • 工具生成的有限描述。
    • 支持多模态时使用独立内容块传递缩略图或图片。

    JSON 召回机制

    不能只提供本地文件路径，还需要统一的结构化召回接口：

    {
  "artifact_id": "artifact_123",
  "json_path": "$.users[100:120]",
  "select": ["id", "name", "risk_score"],
  "limit": 20
}

    召回结果仍然包装为标准 ToolResult，继续接受相同 Token 预算，防止召回操作再次撑爆上下文。

    实验分组

    使用相同模型、问题、工具原始结果和生成参数。

    组别 工具结果处理方式
    A 完整结果直接注入，不做限制
    B 文本序列化后只截取前 50 KB
    C 统一 ToolResult，但只限制 data 条数
    D 统一 ToolResult + Token 预算 + artifact + 结构化召回

    其中 B 组模拟 QwenPaw 当前通用文本裁剪的兜底思路；D 组是本实验目标方案。

    测试数据

    用例一：小型 JSON

    包含状态、数字、短数组，验证小结果不会被不必要压缩。

    用例二：关键字段位于尾部

    构造大型单行 JSON：

    {
  "records": ["大量正常记录"],
  "success": false,
  "error": "最终写入失败"
}

    问题：任务最终是否成功，失败原因是什么？

    预期：B 组可能遗漏尾部错误；D 组必须通过固定 error 字段正确回答。

    用例三：十万行表格

    要求回答：

    • 总行数。
    • 最大值、最小值和平均值。
    • 是否存在失败记录。
    • 某一指定 ID 的记录内容。

    前 3 个问题使用 summary.facts；指定记录通过结构化召回读取。

    用例四：大型日志

    错误放在日志尾部，中间加入大量正常输出。验证是否能同时保留退出码、错误堆栈、头尾信息和完整日志引用。

    用例五：深层嵌套 JSON

    把目标事实放在 6 层以上的对象中，验证对象折叠后能否通过 JSONPath 精确召回。

    用例六：超长字符串和大型单行 JSON

    验证程序不会生成非法 JSON，也不会依赖按行分页恢复单行内容。

    用例七：工具失败和 artifact 保存失败

    验证：

    • 工具失败时错误核心字段不会被 data 挤掉。
    • artifact 保存失败时不会继续裁掉唯一的原始结果。
    • 系统会明确报告降级状态。

    实验步骤

    1. 定义 ToolResult JSON Schema，并使用 Pydantic 或 JSON Schema 校验。
    2. 为 scalar、object、list、table、log 和 fallback 实现 Adapter。
    3. 原始结果超过阈值时保存 artifact，并记录 ID、格式、大小和路径。
    4. 构建只保留固定控制字段的基础上下文对象。
    5. 根据 result_type 对 data 进行分级缩减。
    6. 使用 Qwen3 的 Tokenizer 计算最终结果 Token 数。
    7. 超出预算时重复执行下一缩减等级，直到满足预算。
    8. 将有限 ToolResult 作为 tool 消息发送给模型。
    9. 模型需要完整内容时调用 artifact/JSONPath 召回工具。
    10. 对 A、B、C、D 四组分别重复至少 10 次并记录结果。

    记录指标

    指标 说明
    Prompt Token 工具结果实际占用的输入 Token
    JSON 合法率 注入上下文的 ToolResult 能否被 JSON 解析
    关键字段保留率 状态、错误、事实是否完整保留
    事实回答准确率 模型回答是否与原始 artifact 一致
    局部样本误判率 是否将预览误认为全部数据
    召回成功率 能否根据 artifact 和路径恢复目标内容
    召回附加轮数 完成任务额外需要多少次工具调用
    artifact 完整率 保存结果与原始结果是否一致
    上下文溢出率 是否发生超出模型上下文的请求
    总延迟 Adapter、落盘、Token 计数、模型和召回总耗时

    验收标准

    D 组需要同时满足：

    1. 所有注入上下文的 ToolResult 都是合法 JSON。
    2. ok、result_type、错误核心字段和 artifact 引用保留率为 100%。
    3. 所有 ToolResult 最终 Token 不超过配置预算。
    4. 大型原始结果能够通过 artifact 恢复，并校验哈希一致。
    5. 关键字段位于尾部时，准确率明显高于文本前缀截断组。
    6. 模型不会把有限样本表述成完整数据集。
    7. 召回结果仍受相同预算约束，不发生二次上下文溢出。

    实验结论模板

    实验结束后回答：

    1. 统一 ToolResult 外层协议是否足以覆盖当前工具？
    2. 哪些 result_type 仍需要专用 Adapter？
    3. 固定字段和 summary.facts 是否减少了模型语义提取的不确定性？
    4. 每次工具结果的合理默认 Token 预算是多少？
    5. artifact 保存和召回增加了多少延迟？
    6. 是否采用 D 组作为后续长链路任务的默认工具输出方案？
