    文档读取

    What — 是什么

    文档读取是 RAG 的第一道关卡。把任意格式的文件（PDF、Word、Markdown、PPT、Excel、图片）转成带类型标签的结构化内容单元，供下游切分模块使用。

    核心思路：策略模式——每种文件格式一个独立的加载器，通过扩展名自动分发，互不耦合。新增格式只需写一个新加载器并注册，不改任何现有代码。

    任意格式文件(.pdf / .docx / .md / .pptx / .xlsx / .csv / .jpg / .png ...)
  → 解析 + 打标（heading / table_row / image / paragraph）
  → ContentElement 列表（统一数据结构）
  → 送入切分模块

    Why — 为什么

    文档读取不好，Embedding 再准、Reranker 再强都白费。

    • PDF 没有 <h1> <table> 标签，只有"在 x,y 坐标画了某段文字"。不逐页区分文字层和扫描页，标题跟正文混在一起，表格变成散落文字。
    • 旧格式兼容：.doc 和 .ppt 是微软 Office 2003 二进制格式，没有 Python 库能直接读，必须走外部工具 fallback。
    • 表格不是段落：Excel 和 CSV 是二维结构，直接拼成文本送切分器会把数据切散。
    • OCR 选错引擎（Tesseract 做中文），"线程池"变成"线裎池"，后续全链路污染。

    一句话：文档解析质量 = 检索质量的上限。解析丢了 30% 的结构，后面的 Embedding 再好也只能用 70% 的信息。

    How — 怎么做

    1. 整体架构：策略模式

    DocumentLoaderContext（上下文，持有所有 Loader 策略）
  │
  ├─ 注册表：{扩展名 → Loader 实例}
  │     ".md"   → MdLoader
  │     ".pdf"  → PdfLoader
  │     ".docx" → DocxLoader
  │     ...
  │
  └─ 调用：ctx.load("file.pdf")
        → 取扩展名 .pdf
        → 查注册表 → PdfLoader
        → loader.load(file_path) → [ContentElement, ...]

    为什么策略模式而不是 if-else：新增格式只加 Loader 子类 + 注册一行，不改 Context 和已有 Loader。扩展开放，修改闭合。

    2. 统一数据结构

    DocType = Literal["heading", "table_row", "image", "paragraph"]

@dataclass
class ContentElement:
    content: str       # 文本内容
    doc_type: DocType  # 类型标签 → 决定下游切分策略
    metadata: dict     # 文件名、页码、行号等

    四种标签的含义和下游影响：

    doc_type 含义 下游切分策略
    heading Markdown 标题 # ## ### 或 Word Heading 样式 切分边界，保留层级
    table_row 表格的每一行，以"列头: 值"格式拼接 行内不切，保持数据完整
    image 图片 OCR 后的文本 独立成块，不参与切分
    paragraph 正文段落 标准递归标点切分

    标签在加载时打、不在切分时猜——Loader 知道文档结构（Word 样式名、Markdown # 数、PDF 坐标层级），是最佳的打标时机。

    3. 11 种格式加载器

    格式 解析库 实现方式
    .txt open + chardet 编码检测（GBK/UTF-8）→ 单个 paragraph
    .md 标准文件读取 正则检测 # 层级 → heading/paragraph 交替标注
    .pdf PyMuPDF (fitz) + PaddleOCR 逐页处理：文字层提取 + 大图 OCR（尺寸阈值 0.6）
    .docx python-docx 遍历 XML 元素（CT_P/CT_Tbl）保持文档顺序，Heading 样式判定
    .doc antiword → LibreOffice 两级 fallback：antiword（快，纯文本）→ LibreOffice 转 docx（慢，完整保真）
    .pptx python-pptx 遍历 slide.shapes，按(top, left)坐标排序，递归处理组合形状
    .ppt LibreOffice → pptx 转 pptx 后复用 PptxLoader
    .xlsx openpyxl 首行作列头，后续每行拼为"列头: 值"格式，标注 table_row
    .csv csv + chardet + csv.Sniffer 编码检测 + 分隔符自适应（, ; \t），首行作列头
    .jpg PaddleOCR 整张图送 OCR
    .png PaddleOCR 同上

    4. 关键实现细节

    PDF 逐页混合处理

    银行 PDF 中电子页和扫描页可在同一份文档里混合——前 3 页是电子版产品说明（文字层有内容），第 4 页是扫描的签批单（文字层为空）。处理方式是逐页判断而不是整份文档统一处理：

    for each page:
  ① 取文字层 → 有内容 → 段落/标题进入列表
  ② 查嵌入图片 → 大图（宽或高超过页面 60%）→ 送 OCR
              → 小图（Logo/装饰） → 跳过

    0.6 阈值：低于此值的图，OCR 出来基本是"©2024 Visa Inc."这类装饰性文字，对检索零价值。

    Docx 保持文档顺序

    .docx 中 doc.paragraphs 和 doc.tables 是两个独立列表，但文档中段落和表格是交错排列的。不能分两个列表读——会打乱顺序。解决方式：直接遍历 XML 树，按 CT_P（段落元素）和 CT_Tbl（表格元素）在文档中的实际位置顺序提取。

    旧格式两级 Fallback

    .doc 和 .ppt 是 Office 2003 的 OLE2 二进制格式，python-docx 和 python-pptx 只支持 2007+ 的 OOXML 格式。处理方式：

    antiword（秒级，纯文本提取）
  → 成功 → 返回
  → 失败 → LibreOffice --headless 转 docx/pptx（30-60s，格式保真）→ 复用新版 Loader

    表格→自然语言

    Excel/CSV 是二维结构，不能直接送切分器。转换为自然语言格式：

    原始：
  卡种  | 年费 | 减免条件
  白金卡 | 800  | 消费6笔

转换后（table_row 类型）：
  "卡种: 白金卡 | 年费: 800 | 减免条件: 消费6笔"

    OCR 单例复用

    所有 Loader 共享同一个 OCR 引擎实例——优先加载 GPU 版本（rapidocr_paddle），不可用时自动回退 CPU（rapidocr_onnxruntime）。避免每种格式各自初始化 OCR 导致内存膨胀。

    5. OCR 原理

    OCR 解决一个问题：从像素网格还原离散符号序列。这是一个病态问题——同一个文字可以有不同的字体、大小、旋转角度、光照条件，但最终都要映射到同一个 Unicode 码点。

    中文 OCR 比英文难一个数量级：

    英文 中文
    字符集 26 字母 + 数字 常用 6,763 字（GB2312），全量 20,000+
    字符形态 线性排列，单个字母独立 方块结构，笔画交织（"已"和"己"差 1 像素）
    OCR 策略 逐字母识别 + 拼词 必须整字识别，无法拆笔画

    PaddleOCR 三阶段管线

    输入图片 (H×W×3 像素)
  → DB 检测（圈出每块文字的 bbox 坐标）
  → Cls 方向分类（判断 0°/90°/180°/270°）  
  → CRNN + CTC 识别（bbox 内像素 → 文字序列）

    为什么拆成三阶段而不是端到端：检测和识别对分辨率要求不同。检测需要高分辨率定位边界，识别需要低分辨率 Semantic 特征。一个模型同时做两件事会导致两个任务都做不好。

    DB（可微二值化）— 文字检测

    传统方法用固定阈值二值化——像素值大于 127 的算前景。对于不均匀光照，固定阈值直接失效。DB 的核心思想：让二值化步骤可导，从而融入 CNN 训练。每个像素自适应阈值——阴影处自动降低，亮处自动提高。

    CRNN + CTC — 文字识别

    核心困难：特征帧和字符不对齐。"你好"（2 个字符）经过 CNN 变成 8 个时间步，哪 4 帧对应"你"、哪 4 帧对应"好"——没有标注。CTC 的解法：引入空白标记 ε，最大化所有能折叠成正确标注的路径的概率之和。从根上解决了对齐标注缺失的问题。

    PaddleOCR vs Tesseract

    Tesseract PaddleOCR
    检测 传统 CV（连通域分析 + 固定阈值） DB CNN（可微二值化）
    识别 LSTM + 显式字符切割 CRNN + CTC（端到端）
    中文 非原生设计 原生训练，字符集 6K+
    抗干扰 弱 强

    结论：Tesseract 假设输入是扫描仪扫的干净 A4 纸，PaddleOCR 假设输入可能是手机拍的歪斜发票。RAG 场景文档来源不可控，必须 PaddleOCR。

    误差传播：OCR 这里每错一个字，后续 embedding 向量就偏了、检索就召回了错的上下文、LLM 就基于错误片段回答了——用户只会骂 LLM 胡说八道，不知道是第一步 OCR 埋的雷。

    技术栈

    环节 工具
    架构 策略模式（DocumentLoader ABC + Context + 注册表）
    统一数据 ContentElement（content + doc_type + metadata）
    PDF PyMuPDF (fitz)
    Word python-docx (OOXML) + antiword → LibreOffice (旧格式)
    PPT python-pptx + LibreOffice (旧格式)
    Excel/CSV openpyxl + csv.Sniffer + chardet
    OCR RapidOCR (rapidocr_paddle → rapidocr_onnxruntime 自动回退)
